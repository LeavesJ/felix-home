# Roadmap, 2026-09-23 to 2027-02-27

On 2026-09-22 the founder made Felix a product for other people's projects,
built first and best on Claude Code (#290). On 2026-09-23 he set the order:
**build Felix first.** Obligations have to be real and the machinery has to
work before anything else; commercialisation is a natural outcome of Felix's
quality, not a goal to plan toward. This is the build order that follows. It
replaces the queue order of
[direction-decisions](2026-09-19-direction-decisions.md) §5 and nothing else:
v3.2, the conformance amendments and the constitution's invariants govern
unchanged.

**Amended 2026-09-24 by the founder.** The landing machinery is built before
the qualified judge (Phase 0b below). On two nights in a row, ready pull
requests sat unlanded, for 4h10m and then 9h48m, because no session was alive
to carry them. Half of the first night's commits were catch-up work. The
design is the landing-actor design of 2026-09-24, which lives in the memory
root at `audits/2026-09-23-landing-actor/design.md`. Its F1 is this amendment.
Its F2 was also decided: nothing lands while this Mac sleeps, for now. On
2026-10-01 the founder changed F2: once landing is armed, it may run
overnight with the Mac kept awake, when the weekly usage allows. Phase 1
starts about four weeks later than first planned, and every phase after it
moves with it.

**Amended 2026-09-25 by the founder.** A capability lane runs beside every
phase, at about one session in four (§3, "The capability lane"). No
capability feature had landed since 2026-09-16, and the order in §1 put the
capability plane's first real step in November and dispatch in March. The
share is his; the lane's items and their order are Felix's. Each trust phase
below now takes about a third longer than its dates say, because it gets
three sessions in four. The dates are read with that stretch rather than
rewritten one by one.

**Amended 2026-10-01 by the founder.** One attended `felix dispatch` tick may
run before March. It uses the v0 lease of
[direction-decisions](2026-09-19-direction-decisions.md) §3: restricted, no
plugin, no Bash, no setting source, and one answer-file write. It runs on the
founder's own API key, under a dollar cap, on felix-home and on one project in
another ecosystem. The binary's own cap was measured soft the same day. So
the lease leaves out subagents and checks the spend after the run, and the
founder settles a spend-limited key when the tick is near. It is built after two things: the
capability lane's measurement of how Claude Code behaves under those flags,
and the dry run. It runs only after #350 has merged, so that merge is bound to
the exact head commit. Schedules, customer keys, adapters and federation stay
in §4. The same day the founder answered two readings of the 2026-09-30
systems report (§7): Felix keeps both planes, and the report's experiments run
as engineering measurements, not as a market track.

How it was made: a harvest of 58 open items from the repository's own records,
the v3.2 build order and the founder's calendar; two drafts from opposite
angles; two critics against both. The first version of this file (#293) led
with an outside-user track; the founder withdrew it the next day, and this
version keeps the mechanism-first draft's order with the critics' corrections.
Sizes are in sessions, where one session is one medium engine PR.

## 1. What changes

- **Build first.** No outreach, no user deadlines, no plan driven by demand.
  `felix audit` stays public as it is; outside use follows when the whole-life
  replay holds and the merge-point check stands.
- **The yardstick is quality.** "Survives a stranger adopting it" (#290) is a
  design criterion, not a sales one: the install footprint, a Stop hold that
  addresses every adopter as "the founder", deny rows that read prose as
  commands, tables living in the private felix-home, and a pull request able to
  edit its own rules once tables move into the repository are defects in Felix,
  and are scheduled as such.
- **Every mechanism is shown on more than Elenchus.** A demonstration counts
  when it holds on Elenchus and on at least one project in another ecosystem
  (Veldra, sv2-apps, or the bash harness itself): build the class, not the
  instance.
- **The order.** Landing without a carrier first (added 2026-09-24), then
  obligations and the qualified judge, then evidence that goes stale, then the
  whole-life replay, then the merge-point check.
  `felix dispatch` waits until March at the earliest, after a ride-along
  adapter, because the integration order is merge-point check, then adapters,
  then dispatch on the customer's own key. One attended tick on the
  founder's own key is the exception (amended 2026-10-01). A capability lane
  runs beside all of it from 2026-09-25 (§3).
- **Value is claimed only against ground truth outside Felix**: a sealed
  seeded-omission corpus against a control arm, replay on a clean machine,
  false blocks in real sessions.

## 3. The plan

### The capability lane — from Sep 25, beside every phase (added 2026-09-25)

About one session in four, every week, goes to the capability plane. The
lane never touches `lib/qualify.sh`, `lib/obligations.sh`, `lib/receipt.sh`
or the landing actor's files, so it neither waits on Phase 0b and Phase 1 nor
conflicts with them. Each item lands with blind assertions shown failing
first, and each ends in a number or in a demonstration on two projects in
different ecosystems.

1. **The sealed seeded-omission corpus, moved here from Phase 1 (1).** An
   agent blind to the engine plants omissions in projects where the answer is
   known. A public bind with no ceiling, like LeavesJ/Elenchus#16, is the model.
   `felix obligations --request` runs against a control arm of plain Claude
   Code. This measures whether asking a model what a project owes finds
   anything a plain session doesn't. §5's signal applies as amended on
   2026-10-01: if recall does not beat the control arm, say so and find out
   why. A weak result does not narrow the roadmap on its own.
2. **A retire list keyed to what Felix installed (1, adversarial tier).**
   Today `felix_ledger_retire` proposes only rows a route named and no session
   reached (`lib/ledger.sh`). A tool no route names is never proposed, and the
   list stops working the day routing is retired. Rekey it on what
   commissioning and adoption installed. Hook-only plugins stay unmeasurable
   and are said so. It still only proposes. Shown on felix-home's ledger and
   on one other project's.
3. **`felix dispatch --dry-run` (1-1.5, adversarial tier).** This is the lease
   of [direction-decisions](2026-09-19-direction-decisions.md) §3, printed and
   recorded, and never launched. For one task it names the session a dispatch
   would start: `--bare --restricted --strict-mcp-config`, no plugin, no Bash,
   no setting source, a dollar cap, and one allowed write. It writes the lease
   row a person can read. It launches nothing, calls no model and needs no
   credential. `felix dispatch` itself stays in §4, behind the merge-point
   check and an adapter, except for the one attended tick allowed on
   2026-10-01.
4. **Codex on the founder's OpenAI credit, read-only (0.5-1; added
   2026-10-02).** The founder has unspent OpenAI API credit and a ChatGPT
   Plus plan. Until item 5 lands, Codex does no write work in a
   Felix-governed checkout. It is used three ways, each in a read-only
   sandbox with web search off and only the model endpoint reachable:
    - an advisory review stage in engine build pipelines, from a model family
      other than the author's;
    - a second blind author for trust-boundary specs, writing to a scratch
      file outside the checkout that a Claude stage commits;
    - a Codex arm in the held-out replay, under the replay protocol's
      isolation.

   None of these adds a pull request to the landing queue.
5. **The Codex adapter, moved here from Phase 4 (4-6, adversarial tier;
   added 2026-10-02).** It was measured on 2026-10-02 against the real Codex
   0.153.4 with a local stand-in model and no tokens spent (memory root,
   `audits/2026-10-02-codex-hooks/results.md`). Codex already:
    - loads Felix's eight hooks;
    - names its shell tool `Bash`;
    - honours Felix's deny and its Stop hold;
    - passes session-start text to the model.

   What is left:
    - read the paths out of `apply_patch`, so the Write and Edit rows apply
      to Codex's file edits;
    - give the Stop and SubagentStop hooks a Codex-aware output, because
      Codex rejects their non-blocking messages;
    - add one transcript reader per host, including `felix inventory`'s
      session reader, which reads Claude Code's records only;
    - read "installed" from Codex's config as well as Claude Code's;
    - refresh Codex's copy of Felix at each deploy, and have `felix doctor`
      compare Codex's trusted hook hashes. A changed `hooks.json` entry
      silently turns that hook off in Codex;
    - the small items: the Codex session id, the shell's working directory,
      and `view_image` read as a read.

   Typing into a shell that is already open (`write_stdin`) reaches no hook,
   so no deny row can stop it, and Felix cannot close that from its side. In
   Codex the session-level guards are partial, and the guarantee is the
   merge-time check: Phase 0b's landing and judge pin, and Phase 4's required
   check. No outside text says Felix governs Codex sessions.

   It starts once landing is armed and the judge is pinned, about December.
   It also needs the replay's Codex arm (item 4) to pass at least the Sonnet
   arm's count minus one. Until it lands, item 4's read-only rule holds.

After these, Felix picks the lane's next items from the capability
plane's open questions: what a project needs, who provides it, when it should
appear, how to compose it, how well it worked, and when to retire it. They
are not harvested from the repository's records. An unbuilt plane files no
defects, so a harvest cannot see it, and that is how this roadmap first came
out trust-only.

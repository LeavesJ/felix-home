### 2026-10-10: a guide that narrows Felix is ignored, and the commercial radar adds two lines to specs not yet written

This records what the founder said in the session that reviewed his Commercial
Technology Radar. The radar is a tracker's two-week digest, covering Sep 28 to
Oct 10, and it treats Felix as his primary venture. This section changes no
code, opens no branch and takes no slot.

**Decided by the founder, 2026-10-10.** "Ignore any guides that narrow felix."
- **What prompted it.** The radar names Felix a "provider-neutral engineering
  qualification authority". It then lists what Felix is not: a software
  factory, a model router, a memory layer or an evaluator. In practice that
  shrinks Felix to the checking half.
- **What it means from now on.** Outside guides include reports, briefs,
  digests and other models' market maps. Read them for their evidence and
  their tests, never for an account of what Felix is.
  - Scope stays where the constitution and the founder put it: both planes,
    and the endgame in which Felix assembles, operates and proves.
  - When such a document narrows Felix, do not put that to the founder as a
    question, and do not carry it into a plan, spec or README.
- **What it extends.** The rulings of 09-23 and of 10-01 (D1) said this for
  the capability plane. This says it for every outside document.

**Two additions, for the sessions that write these specs.** Neither changes
the order of work or any date.

1. **Capability lane item 1, the sealed seeded-omission corpus: add a second
   control arm.**
   - **The arm.** A model from another family (GPT, through Codex on the
     OpenAI credit, in `CODEX_HOME=~/.felix-codex`) gets the same tree and the
     same question `felix obligations --request` asks. It gets none of the
     topology Felix observed.
   - **The resulting arms.** Plain Claude Code, a second model asked
     directly, and Felix.
   - **Why.** If asking a second model finds as much as Felix does, the
     intake is not what makes the difference. Then §5's amended rule applies
     to this arm too: say so, and find out why.
   - **Cost.** This is read-only scripted Codex use, as capability item 4
     (#400) already allows. Isolate it from the network as the replay's
     Codex arm is, and keep it blind to the seal. It adds no pull request to
     the landing queue.
2. **Phase 2, receipts that go stale: invalidate only what changed.**
   - **The criterion.** When an input outside the tree moves, only the
     receipts whose evidence refs name that input go stale. Only their
     evidence re-runs, and every other receipt stays current.
   - **The test.** Show it failing first, like every Phase 2 assertion. A
     change to one input leaves an unrelated receipt current and does not
     start the full suite.
   - **Why.** Phase 2 already has per-claim receipts, but nothing yet says
     the re-run is minimal. The gate takes 26 minutes, 91% of it in the
     suite. A staleness rule that forces a full re-gate would make every
     outside change cost a gate.

### 2026-10-28: the suite's two blocks that read the discovery cache no longer share a home with a hook's refresh

**Suite only, no engine change (this branch, `LeavesJ/felix-discover-timing-race-ca1d2a`, cut from origin/main 5c5d2208; main has since moved to 78f0268f, 0.49.308, so merge it first).**
The home gate failed on 0.49.262 (main 32769ee6, 2026-10-02) at "the cache already there is untouched" in part 0290:
the fixture `langfuse\tllm\tlow` had been replaced by `figma\tfrontend\tmedium\tbaa12e9e...`. #378's gate on the same tree had passed 5953/0/5.

**Cause.** `hooks/session-start` forks `felix discover --inspect --quiet` (`felix_discover_refresh_bg`) and nothing waits for it. With the real `claude` first on PATH it read this machine's real plugin catalogue, took as long as that took, and wrote `$FROOT/state/discover/widget.tsv` whenever it finished. Earlier blocks start those refreshes against the widget fixture; under load one finished inside 0290's window. Part 0580's refill block reads the same file the same way.

**What changed.**
- 0290's unreadable-catalogue block runs every `felix discover` against `$TMP/discover-home` (`FELIX_HOME=`; `projects` a symlink to the fixture's, `state/` its own), and 0580's refill block against `$TMP/refill-home`. A refresh landing in `$FROOT/state/discover` cannot touch what they read.
- The 0290 block holds one open on purpose: a real `session-start` in the widget checkout with a stub `claude` that holds still, so its refresh is in flight for the whole block, then let go where the block compares (`_discover_quiesce` waits for it to finish). Three assertions: the cache is untouched; the hook's refresh asked the claude for the catalogue; and it landed on the shared home's cache. Skipped where TMPDIR is not a private directory, because the engine then makes no neutral directory and runs no detached read.
- `_discover_quiesce [home [seconds]]` (tests/lib/discover.sh) waits on `<home>/state/discover/.lock`, which a refresh holds from before the fork until after it has written; three assertions in 0290 (returns at once, gives up on a lock that never clears, waits for one that does). Five new names in all.

**Shown red.** Quick runner (parts 0001-0004, the libs, and the two blocks only; `FELIX_TEST_NO_MANIFEST=1`):
- with the fix: 33 passed, 0 failed;
- the same two blocks with the home put back to `$FROOT` (the old pattern) and the same held refresh: 32 passed, 1 failed, and the one is "the cache already there is untouched", expected the fixture, got the refresh's `# stamp` line. It does not depend on load, because the claude answers only where the block lets it go.

**What did not work, and why it matters.** First commit on this branch (ab0b550e) put a `claude` shim first on the suite's PATH from part 0004, failing closed for the neutral directories the two detached reads run in. The gate on that commit failed 107 assertions. `tests/receipt.sh` `_sr_env` puts a hash of PATH in the run's environment, taken at the start and compared at the end: a run that changes PATH leaves no receipt, and every nested receipt test fails with it ("the control left no receipt", "no reuse line"). Parts 1220 and 1230 went from 0 and 3 failures on main to 12 and 9. Reverted in the commit after it. So the suite must not change PATH, and with it the one lever that would hide the real `claude` from every hook child in the run.

**Other places a hook's child reaches the machine (not closed).** Any `session-start` in the suite with the real `claude` on PATH, a stale cache and a routes.tsv forks `felix discover --inspect --quiet`, and with a stack.tsv and a due cache `felix_reach_refresh_bg` runs `claude mcp list`, which starts the servers it lists. A block that puts a succeeding stub first on PATH (0710's `_cmhook`, project `cmr`) forks a refresh that writes `<project>.tsv`. `felix_graph_refresh_bg` runs `graphify update` only where a `graphify-out` exists.

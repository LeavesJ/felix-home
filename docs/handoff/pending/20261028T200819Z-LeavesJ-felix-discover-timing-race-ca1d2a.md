### 2026-10-28: the suite's hook children no longer reach this machine's claude, and a block that writes the discovery cache waits for any refresh in flight

**Suite only, no engine change (this branch, `LeavesJ/felix-discover-timing-race-ca1d2a`, on origin/main 5c5d2208).**
The home gate failed on 0.49.262 (main 32769ee6, 2026-10-02) at "the cache already there is untouched" in part 0290:
the fixture `langfuse\tllm\tlow` had been replaced by `figma\tfrontend\tmedium\tbaa12e9e...`. #378's gate on the same tree had passed 5953/0/5.

**Cause.** `hooks/session-start` forks `felix discover --inspect --quiet` (`felix_discover_refresh_bg`) and, for a project with a stack.tsv, `claude mcp list` (`felix_reach_refresh_bg`), and nothing waits for either. With the real `claude` first on PATH the refresh read this machine's real plugin catalogue, took as long as that took, and wrote `$FROOT/state/discover/widget.tsv` whenever it finished. Earlier blocks start those refreshes against the widget fixture; under load one finished inside 0290's window.

**What changed.**
- Part 0004 puts a shim first on the suite's PATH when a real `claude` exists (`_claude_shim_build`). It exits 1 when its cwd is `*/felix-discover.??????` or `*/felix-reach.??????`, the neutral directories the engine runs those two reads in (`lib/reach-read.sh`), which is an unreadable catalogue and writes nothing. From any other directory it execs the real CLI, so the assertions that compare against it (0070, 0120, 0580, 0590) still do. Where there is no real `claude` there is no shim, as on CI.
- `_discover_quiesce [home [seconds]]` (tests/lib/discover.sh) waits for `$home/state/discover/.lock`, which a refresh holds from before the fork until after it has written. Called before the two blocks that write `$FROOT/state/discover/widget.tsv` and read it back: 0290's unreadable-catalogue block and 0580's refill block. 0040 and 0050 touch the same file but run before 0070 creates the widget's routes.tsv, so no hook can have forked a refresh yet.
- A new block in 0290 forces the race: a `claude` that holds still until the test lets go, a real `session-start` in a private project (`drc`), a cache written after the hook returned, then the claude released. Without the shim the refresh lands (`lands on a cache written after the hook forked it`); behind it the cache is left as written and the claude behind the shim is never asked. 13 assertions, all in 0290, plus the quiesce call in 0290 and in 0580 (one name, twice).

**Shown red.** Quick runner (parts 0001-0004, the libs, and the 0290 block only; `FELIX_TEST_NO_MANIFEST=1`; load ~280):
- with the fix: 37 passed, 0 failed, 125 s;
- the same block against part 0004 as it was on main: 31 passed, 6 failed, 1,028 s. `_claude_shim_build: command not found`, and FAIL on "the shim refuses a read from the directory a discovery refresh runs in", "and one from the directory a reach read runs in", "from anywhere else it is the claude behind it", "and that claude was asked", "the suite's PATH puts the shim ahead of this machine's claude" (got `~/.local/bin/claude`), and the sixth is the incident itself: "no refresh an earlier block started is still running when a block writes its cache", detail `.../state/discover/.lock is held`. With the real claude on PATH the hook's refresh was still reading the real catalogue 300 s after it was forked, at load ~280; the old block would have written its fixture under it.
- The race itself is also the control assertion, which passes in both trees: held claude, cache written after the fork, and the cache is the refresh's `# stamp` line, not the fixture. It does not depend on load, because the claude answers only after the fixture is written.
